# 精度確認（validation）

UI Anatomy Scanner の自動判定が、実在するページでどのくらい正しいかを、外部ツールと突き合わせて測る仕組みと、その記録です。

## 先に結論

- **客観的に確かめられる検査**（文字のコントラスト、アイコンのみのボタンの名前、操作領域のサイズ、画像の代替テキスト）は、アクセシビリティ検査エンジン axe-core との照合で測った。修正後に**初めて走らせた未見14ページ**では、コントラスト不足の検出が**再現率96%（143/149）・適合率100%**、ボタン名の検出が**再現率91%（51/56）**だった。
- ただし、**最初の測定（修正前）では、同種の未見ページでコントラストの再現率が48%（36/75）しかなかった**。原因は、レイアウトを実際のブラウザと違う高さで描いていたことなどで、検証によって見つかり、修正した。数値の変遷は下の「測定の記録」に残している。
- **ニールセン10原則に基づく指摘（H1〜H10）の妥当性は、外部ツールに正解がないため、まだ測れていない。** 事実を独立に確かめられる H1・H10 は別実装と照合した（一致）が、それ以外は人手の採点が必要で、採点シートと集計スクリプトを用意した段階（採点は未実施）。
- 対象は**実在のオープンソーステンプレート45ページ（MIT）**で、**ライブのWebサイトではない**。この実行環境のネットワーク制限で、実サイトのURLを取得できなかったため。自分のPCで実サイトを測る手順は下にある。

## 何をどう測ったか

| 項目 | 内容 |
|---|---|
| 対象 | StartBootstrap・AdminLTE の実在テンプレート（コミット固定）。EC・管理画面（業務システム）・ランディング・ブログ・問い合わせ |
| 基準 | axe-core 4.14 の違反。ツールの検出と、要素の位置・大きさ（誤差6〜8px）で照合 |
| 検査 | コントラスト（color-contrast）、画像の代替テキスト（image-alt）、ボタンの名前（button-name / input-button-name、およびボタンとして扱った要素の link-name）、操作領域（target-size） |
| 指標 | 再現率＝一致÷axe違反、適合率＝一致÷(一致＋axeが合格とした誤検出)。axeが評価しなかった検出は「判定不能」として別に数え、分母に入れない |
| ボタン検出 | `button`・`[role=button]`・Bootstrapの`.btn` を持つ可視要素を正解とした再現率 |
| 事実確認 | H1（主ナビに現在地の印がない）・H10（見えているヘルプ導線がない）を、ツールとは別に書いたDOM検査と照合 |
| 陽性対照 | 違反をわざと入れた自作ページ（`fixtures/positive-control.html`）。検出できるか、基準のずれがないかの確認 |

### データセットの分け方（重要）

ツールを直しながら同じページで測ると、そのページに合わせた数字になる（過学習）。そこで次のように分けた。

| セット | ページ数 | 位置づけ |
|---|---|---|
| 開発セット（dev） | 14 | ツールの修正中に見ていたページ。**調整済みで、精度の推定には使えない** |
| holdout 1 | 16 | 最初は未見として測ったが、失敗の原因調査に使ったため、現在は調整済み。**初回測定は `results/history/` に保存** |
| holdout 2 | 14 | 修正が一段落した後に初めて走らせたページ。**精度の推定には、この結果を使う**。初回測定も `results/history/` に保存 |
| 陽性対照 | 1 | 自作の違反例 |

## 結果（現在のツール）

`results/RESULTS.md`（自動生成）に全表がある。未見ページ（holdout 2）の要点:

| 検査 | axe違反 | 一致 | 見逃し | 誤検出(axeは合格) | 判定不能 | 適合率 | 再現率 |
|---|---|---|---|---|---|---|---|
| 文字のコントラスト比 | 149 | 143 | 6 | 0 | 39 | 100% | 96% |
| アイコンのみのボタンの名前 | 56 | 51 | 5 | 0 | 5 | 100% | 91% |
| 操作領域のサイズ | 0 | 0 | 0 | 0 | 3 | — | — |
| 画像の代替テキスト | 0 | — | — | — | — | — | — |

- 画像の代替テキストと操作領域は、実在ページに違反が（ほぼ）なく、**実在ページでは評価できなかった**。陽性対照では検出できた（画像3/3、操作領域2/2）。
- 見逃しは、すべて1ページ（AdminLTEのダッシュボード）に集中。JavaScript（チャート・カレンダー）で描かれる領域のレイアウトが、スクリプトを実行しないツールの描画と違うため、同じ要素を別の位置に見ていた。
- 「判定不能39件」は、axeも「要確認」とした34件（背景が画像・重なりなどで、両者とも確定できない）と、axeが評価しなかった5件（チャート領域の位置のずれ）。

### 検証で見つかった問題と、直したこと

| # | 見つかった問題 | 直したこと | 見つかったセット |
|---|---|---|---|
| 1 | 長いページの下の部分が、解析範囲（3,000px）の外だった | 上限を12,000pxに引き上げ、切り捨てた場合は明示 | 開発 |
| 2 | ボタン名を `aria-label`・`title` だけで見ていた | `aria-labelledby`・内側の画像の `alt`・`svg` の `title`・`value` も見る | 開発 |
| 3 | 小さな操作領域に、WCAG 2.5.8 の「間隔の例外」がなく、axeが合格とする要素を指摘していた | 24pxの円が他の操作要素と重ならなければ合格にする | 開発 |
| 4 | 画像の上に重なった文字を、白背景と思い込んで指摘していた | 文字の下に別要素の背景があるときは判定しない（のちに、自身や祖先の不透明な背景が先にあれば、その色を使うよう精密化） | 開発・holdout 1 |
| 5 | H1（現在地の表示なし）が、`li.active` を見ず、サイドバーをナビと認識しておらず、補助ナビだけを根拠に指摘していた | 祖先の `active` も見る／サイドバーのリストもナビとして扱う／主ナビのどれかに印があれば指摘しない | 開発（事実確認） |
| 6 | H3（戻る・キャンセルなし）が、問い合わせフォームなどでも出ていた | 入力欄が6個以上の長いフォームに限定 | 開発（目視） |
| 7 | 全高のiframeで描くと、`100vh`・固定サイドバーが伸び、実際の1280×800の表示と配置が変わっていた（4ページで+80〜130%） | 解析は常に実際の1280×800で行い、表示のときだけ全高にする。位置がずれるページには警告を出す | holdout 1 |
| 8 | 不透明度（`.disabled` などの `opacity`）を、コントラストに反映していなかった | 要素と祖先の不透明度を反映 | holdout 1 |
| 9 | 内側のスクロール領域の下のほうが、見えない要素として扱われていた | 内側のスクロール領域の中の要素は対象にする | holdout 1 |
| 10 | 無効（`disabled`）な選択リストの `option` を、低コントラストとして指摘していた（WCAGは対象外） | 無効なコントロールの子要素は対象外にする | holdout 2 |

**注意**: 4〜6は開発セットを見ながら、7〜9はholdout 1の失敗の原因調査で、10はholdout 2の調査で直した。そのため、それぞれのセットは、直した後は「調整済み」になり、精度の推定は、直した後に初めて走らせたセットの初回測定だけが対象になる。現在の holdout 2 の数値も、#10 を直した後は調整済みの値で、**本当に未見の推定値は、初回測定（`results/history/holdout2_first_run_64847c4`）**。

## 残っている限界

- **JavaScriptで描かれる領域**（チャート・カレンダーなど）は、スクリプトを実行しないため、実際の画面とレイアウトが変わる。ページ全体が影響を受けることがある。
- **対象に偏りがある**。Bootstrap系の英語のテンプレートが中心で、日本語のサイト、独自CSSの大規模サイト、SPAは含まれていない。
- **Webフォントとアイコンフォントは入っていない**（実行環境のネットワーク制限で、CDNをスタブに置き換えたため）。文字の幅・高さが、実際と少し違う可能性がある。
- 「判定不能」（背景が画像・グラデーション・重なり）は、精度が確定していない領域。
- 実装者と評価者が同じ（AI）で、**評価者による偏り**がありうる。H1・H10の事実確認は、同じ作者が書いた別実装との照合で、独立した検証ではない。
- axe-core 自身にも誤り・未対応がある。ここでの「正解」は、あくまで axe-core の判定。
- ニールセン系の指摘（H1〜H10）の**妥当性**は、まだ測れていない。

## ニールセン系の指摘の評価（採点シート）

正解のない主観的な指摘は、人の採点で評価する設計にした。

1. `results/rating_sheet.csv` に、ツールの全指摘（このコーパスで約170件）が並んでいる
2. 評価者が `rater1`（2人目は `rater2`）の列に、次のどれかを入れる:
   - **妥当**: 内容が事実で、そのページの種類にとって実際に問題になりうる
   - **疑わしい**: 事実だが、そのページの文脈では問題とは言いにくい（例: 問い合わせフォームにキャンセルがない）
   - **誤り**: 内容が事実と違う
3. `node score_ratings.js results/rating_sheet.csv` で、評価者ごとの妥当率、原則ごとの内訳、2人の一致率とCohenのκを出す

採点は未実施。**最終判断は人間が行う前提**で、AIは採点していない。

## 再現手順

```bash
cd anatomy-scanner/validation
npm install                  # axe-core と playwright
npx playwright install chromium
node fetch_corpus.js         # 実在テンプレートをコミット固定で取得（.corpus/、Gitには含めない）
node run.js                  # 全ページ → results/RESULTS.md, results.json, rating_sheet.csv
node run.js --set holdout2   # 特定のセットだけ
```

- クラウド環境などで外部CDNに届かない場合は、自動で npm の固定バージョン・スタブ・代替画像に置き換えて実行する（`lib/offline.js`）。
- 環境変数: `PLAYWRIGHT_MODULE`（playwrightの場所）、`CHROMIUM_PATH`（Chromiumの実行ファイル）

### 実サイトで測る（自分のPC）

```bash
# urls.txt: 1行1URL（空白のあとにラベル）。# で始まる行は無視
echo "https://example.com/ サンプル" > urls.txt
node run.js --live urls.txt
```

- ネットワークが必要。ページは実際のブラウザで描画し、描画後のDOMをツールに渡して、同じページをaxe-coreでも検査する。JavaScriptで描かれるサイトは、描画後のDOMを使う。
- 出力は `results/results_live.json`・`RESULTS_live.md`・`rating_sheet_live.csv`。
- **他人のサイトを検査する場合は、利用規約とアクセス頻度に配慮してください。** 結果ファイルに、ページのHTMLは含まれない（URL・要素の位置・抜粋のみ）が、公開する場合は対象サイトの扱いを確認してください。

## 注意

- 取得した第三者のテンプレートは、リポジトリに含めない（`.corpus/` は無視設定）。いずれもMITライセンスで、取得元のURLとコミットは `targets.json` にある。
- `results/history/` には、各時点の初回測定の結果を、修正の前後を比較できるように残してある。
