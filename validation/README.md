# 精度確認（validation）

UI Anatomy Scanner の自動判定が、実在するページでどのくらい正しいかを、外部ツールと突き合わせて測る仕組みと、その記録です。

## 先に結論

- **客観的に確かめられる検査**（文字のコントラスト、アイコンのみのボタンの名前、操作領域のサイズ、画像の代替テキスト）は、アクセシビリティ検査エンジン axe-core との照合で測った。修正後に**初めて走らせた未見14ページ**では、コントラスト不足の検出が**再現率96%（143/149）・適合率100%**、ボタン名の検出が**再現率91%（51/56）**だった。
- ただし、**最初の測定（修正前）では、同種の未見ページでコントラストの再現率が48%（36/75）しかなかった**。原因は、レイアウトを実際のブラウザと違う高さで描いていたことなどで、検証によって見つかり、修正した。数値の変遷は下の「測定の記録」に残している。
- **ニールセン10原則に基づく指摘（H1〜H10）の妥当性は、外部ツールに正解がないため、まだ測れていない。** 事実を独立に確かめられる H1・H10 は別実装と照合した（未見14ページでは H1 11/11・H10 14/14 で一致。holdout 1 では H1 13/14・H10 15/16）が、それ以外は人手の採点が必要で、採点シートと集計スクリプトを用意した段階（採点は未実施）。
- スクリーンショット入力（OCR）の精度も、DOMを正解にして測った（[OCR（スクリーンショット入力）の精度](#ocrスクリーンショット入力の精度)）。未見に近い30ページで、文字の検出率90〜94%・誤り率3〜5%、コントラスト判定は適合率100%。ボタン・入力欄の候補は、再現52〜76%・適合率63〜67%と弱い
- **日本語**：デジタル庁デザインシステムの実装例（MIT）の部品ページ23件と、自作の日本語5ページで、DOM解析をaxeと突き合わせた。**日本語の実在ページでは、初回に誤検出が1件**（ボタンの中のアイコン `<svg role="img" aria-label>` が名前になるのに「名前なし」と指摘）見つかり、修正した（#14）。それ以外は、誤検出0・ボタン検出45/45。日本語の自作ページは、コントラスト9/9で一致
- 対象は**実在のオープンソーステンプレート45ページ（MIT）と、日本語28ページ**で、**ライブのWebサイトではない**。この実行環境のネットワーク制限で、実サイトのURLを取得できなかったため。自分のPCで実サイトを測る手順は下にある。

## 残っている限界

- **JavaScriptで描かれる領域**（チャート・カレンダーなど）は、スクリプトを実行しないため、実際の画面とレイアウトが変わる。ページ全体が影響を受けることがある。
- **対象に偏りがある**。Bootstrap系の英語のテンプレートが中心で、日本語のサイト、独自CSSの大規模サイト、SPAは含まれていない。
- **Webフォントとアイコンフォントは入っていない**（実行環境のネットワーク制限で、CDNをスタブに置き換えたため）。文字の幅・高さが、実際と少し違う可能性がある。
- **アニメーションの途中の状態は測らない**。有限のアニメーションは終了状態で、不透明度を繰り返し変えるもの（点滅）は最も見える状態で判定する。axeは実行時点の途中の透明度で判定することがあり、その場合は両者がずれる（ツールの見逃しとして数えられるが、実際にはどの瞬間を測るかの違い）。
- **画面外・隠れた要素の判定は簡易**。祖先の `opacity`・`display`・畳まれた `overflow` は見るが、`transform:translateX` で画面外に追い出したスライド（カルーセル）、`clip-path`、他要素で覆われた要素は判定しきれない。スクロールで現れるアニメーション（`opacity:0` の途中）は、解析時点で見えていなければ対象外になる。
- 「判定不能」（背景が画像・グラデーション・重なり）は、精度が確定していない領域。
- 実装者と評価者が同じ（AI）で、**評価者による偏り**がありうる。H1・H10の事実確認は、同じ作者が書いた別実装との照合で、独立した検証ではない。
- axe-core 自身にも誤り・未対応がある。ここでの「正解」は、あくまで axe-core の判定。
- ニールセン系の指摘（H1〜H10）の**妥当性**は、まだ測れていない。

## ニールセン系の指摘の評価（採点シート）

正解のない主観的な指摘は、人の採点で評価する設計にした。

1. `results/rating_sheet.csv` に、ツールの全指摘（このコーパスで約170件）が並んでいる
2. 評価者が `rater1`（2人目は `rater2`）の列に、次のどれかを入れる:
   - **妥当**: 内容が事実で、そのページの種類にとって実際に問題になりうる
   - **疑わしい**: 事実だが、そのページの文脈では問題とは言いにくい（例: 問い合わせフォームにキャンセルがない）
   - **誤り**: 内容が事実と違う
3. `node score_ratings.js results/rating_sheet.csv` で、評価者ごとの妥当率、原則ごとの内訳、2人の一致率とCohenのκを出す

採点は未実施。**最終判断は人間が行う前提**で、AIは採点していない。

## OCR（スクリーンショット入力）の精度

画像から読み取った文字・文字の大きさ・色・ボタンの位置が、**DOMを正解とした場合に**どのくらい合うかを測りました（`ocr_eval.js`）。ページを描画して、DOMから「文字の行・大きさ・色・背景色・ボタンの位置」を正解として取り出し、同じ状態のスクリーンショットをOCRにかけて照合します。

### 方法
- **文字の読み取り**：正解の各行の範囲にある単語を並べ、正解の文字列との編集距離（空白は無視、NFKC正規化）で採点。「検出率」は類似度80%以上の行の割合、「CER」は文字の誤り率、「余計な文字」は正解の範囲に入らない文字の割合。視覚的に隠した文字（スクリーンリーダー用）は正解に含めない
- **文字の大きさ**：正解のCSSの `font-size` との比（行の検出に成功したもののみ）。**コントラスト**：推定した文字色・背景色から出した比と、DOMの色から出した比を比べ、「基準（通常4.5:1／24px以上3:1）未満か」の一致を採点。背景が単色でない行は除く。**基準の±4%以内は、推定の誤差で判定が割れるため、別に数えて除く**（件数を表に記載）
- **ボタン・入力欄の候補**：DOMのうち「枠（背景色か枠線）が見えて、文字のあるボタン」と「枠のある入力欄」を正解とし、検出した枠との重なり（IoU 0.5以上）で照合。枠が見えないもの（文字だけのリンク・アイコンだけのボタン）は、見た目から判別できないため、正解に含めない
- **セットの扱い**：英語の開発14ページと、日本語（自作5ページ・実在23ページ）は、仕組みの調整に使った（**調整済み**）。holdout 1・2（英語30ページ）は、OCRの仕組みの調整には使っていないが、下の経緯のとおり、一部の設定は結果を見たあとで決めたため、**完全な未見ではない**。画像は1280px幅・DPR 1（Retina相当は2倍も測定）、高さは先頭3,000px（`--maxh`）まで
- **日本語の実在ページ**：デジタル庁デザインシステムの実装例（[digital-go-jp/design-system-example-components-html](https://github.com/digital-go-jp/design-system-example-components-html)、MIT）の部品ページ23件（`targets.json` の `ja-real`）。日本語の実際のUI（フォーム・表・バナー・カード・タブなど）だが、**1画面に部品が1〜数個だけの小さなページ**で、文字は約230行。Webフォントはこの環境では取得できず、システムの日本語フォントで描画

- **ボタン・入力欄の候補**は弱い：英語の未見に近い30ページで、再現率 55〜84%、適合率 64〜66%。日本語の実在ページ（調整済み）で、再現73%・適合96%。表のセル・カードの枠・バッジを、ボタンと取り違える／入力欄の薄い文字（プレースホルダー）を読み落とす、などが残っている

### 限界
- 写真・グラデーション・半透明の上の文字、白と薄い色の組み合わせは、読み取れない／色を誤ることがある（正解がDOMで取れない画像上の文字は、評価に含まれない）
- ボールド・斜体・書体は推定しない。1行に大きさの違う文字が混ざる場合は、行の代表値になる。縦書き・回転・約8px未満の文字は対象外
- JPEGなど圧縮された画像は、色の推定が乱れる（評価はPNG）
- 評価の対象は、**Bootstrap系の英語テンプレートと、日本語のデザインシステムの部品ページ・自作ページ**。**日本語の実際のWebサイト（広告・写真・凝ったデザイン）、ダークモード、デザインツールの書き出しは、まだ測れていない**。手元で測るには、`node ocr_eval.js --live urls.txt`
- 正解にした「ボタン」は、DOMで枠が見えるものに限る。評価はDOMの照合で、人が見て「ボタンに見える」かどうかの採点は、行っていない
- OCRエンジンと言語データは、公開環境ではCDN（jsDelivr）から取得する。CDNからの取得は、この実行環境のネットワーク制限で自動検証できていない（ローカルで同じファイルを配った環境では確認済み）。公開URLでの動作は、手元のブラウザで確認してください

### 実サイトで測る（自分のPC）

日本語の実サイトで測るときは、`urls_ja.example.txt` を `urls_ja.txt` にコピーして、対象のURLに書き換え、次の2つを実行します（1サイト1〜2ページ。他人のサイトは、利用規約とアクセス頻度に配慮）。

```bash
node run.js --live urls_ja.txt --out results_ja      # DOM解析を、axe-coreと突き合わせる（--explain / --diag で原因調査）

```

最初の結果は、直す前に `results/history/` に日付つきで保存してください（直すと、そのサイトは調整済みになります）。


```bash
# urls.txt: 1行1URL（空白のあとにラベル）。# で始まる行は無視
echo "https://example.com/ サンプル" > urls.txt
```
